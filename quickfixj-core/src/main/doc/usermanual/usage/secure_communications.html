Secure Communications with QFJ

Java Secure Sockets

This technique relies on the MINA SSL I/O filter.

The default usage of SSL is very simple. Just add the following setting to your QFJ settings file. 

SocketUseSSL=Y
This setting must be used for both acceptors and initiators. If you need to use a specific SSL certificate, configure your session like below. 
SocketUseSSL=Y
SocketKeyStore=[your key store path]
SocketKeyStorePassword=[your key store password]
If certificates require authentication additional settings must be provided. 
SocketTrustStore=[your trust store path]
SocketTrustStorePassword=[your trust store password]
Acceptor certificates are always authenticated by the initiator. Authenticating client certificates require the following setting. 
NeedClientAuth=Y
Example acceptor configuration with client certificate authentication.

StartTime=00:00:00
EndTime=00:00:00

ConnectionType=acceptor
HeartBtInt=30

Supplying SSL contexts from the application

By default, QuickFIX/J loads the key and trust stores named in the settings from the file system or classpath. An application can instead supply the SSLContext itself through an SSLContextProvider, e.g. when the stores come from a secrets manager and should stay in memory. For example, with stores provided as Base64-encoded environment variables:

char[] password = System.getenv("FIX_KEYSTORE_PASSWORD").toCharArray();
KeyStore keyStore = KeyStore.getInstance("PKCS12");
keyStore.load(new ByteArrayInputStream(Base64.getMimeDecoder().decode(System.getenv("FIX_KEYSTORE_B64"))), password);
KeyStore trustStore = KeyStore.getInstance("PKCS12");
trustStore.load(new ByteArrayInputStream(Base64.getMimeDecoder().decode(System.getenv("FIX_TRUSTSTORE_B64"))),
        System.getenv("FIX_TRUSTSTORE_PASSWORD").toCharArray());

KeyManagerFactory kmf = KeyManagerFactory.getInstance(KeyManagerFactory.getDefaultAlgorithm());
kmf.init(keyStore, password);
TrustManagerFactory tmf = TrustManagerFactory.getInstance(TrustManagerFactory.getDefaultAlgorithm());
tmf.init(trustStore);
SSLContext sslContext = SSLContext.getInstance("TLS");
sslContext.init(kmf.getKeyManagers(), tmf.getTrustManagers(), null);

SocketInitiator initiator = SocketInitiator.newBuilder()
        // ... application, store factory, settings
        .withSSLContextProvider(sslConfig -> sslContext)
        .build();

The provider is set with withSSLContextProvider on the builders of SocketInitiator, SocketAcceptor and their threaded variants; without it, the configured stores are loaded as before. The provider receives the SSLConfig of the session or acceptor address, so it can return different contexts, e.g. a different client certificate per counterparty, and delegate to SSLContextFactory.getInstance(sslConfig) for stores that should still be loaded from files.

  • SocketUseSSL=Y is still required. Only the context comes from the provider; protocols, cipher suites, NeedClientAuth, SNI and endpoint identification are still applied from the settings, while store settings are not used.
  • If the provider throws a GeneralSecurityException or returns null, the session (initiator) or listening address (acceptor) fails to initialize, subject to ContinueInitializationOnError. There is no implicit fallback to the default behavior.
  • The provider is called whenever an SSL filter is set up: once per listening address when an acceptor starts, and once per session when an initiator starts (and again if its I/O connector is reset). Return a new context to pick up rotated credentials on the next start, or supply a key or trust manager that reloads its material to rotate without restarting.
  • Contexts created by SSLContextFactory have their trust managers wrapped so that a RuntimeException thrown during certificate validation is reported as a CertificateException. A supplied context is used as is; wrap its trust managers with X509TrustManagerWrapper.wrap(...) to get the same behaviour.
